## Unreleased

- **The worked example's exports ship.** `plans/example/exports/` holds the three invented files the example cites (`visits.csv`, `cancellations.csv`, `exit-survey.csv`), written from a fixed seed by `make-exports.js` beside them, so anyone can recount every number in the plan and ledger. The plan's opening paragraph says where they are. A new test, `tests/process/example-exports.test.js`, recomputes every ledger number from the files and fails on any mismatch, and checks that the generator still writes the same bytes.
- The README says the check compares every number on the slides with a ledger that records its source, which is what `carousel-check` does. Recomputing from the source happens at build and in the fidelity reviewer.
- `carousel-check` says plainly that `checklist 9 of 9` with item 9 under Waiting on you is the form to use when no render can be exported. The worked example's Check section no longer says the checklist has 9 items: it has 10, and the count leaves out the deferred render item.
- `docs/build-your-engine/rigor.md` records this repository's own mutation round before 1.0.0.

## 1.0.1

- The installer's usage text names `npx carousel-os` when it runs from the npm package, and the script path when it runs from a clone.
- The README opens with the install command, badges for npm, CI and the license, and a fuller description of what ships.
- The package description on npm matches the repository.
- **One skill to download.** `skills/carousel-os/SKILL.md` is a single skill you can drop into your skills folder like any public skill. When you ask your agent to set up Carousel OS, it checks the project, asks once before running `npx carousel-os init .`, runs `doctor`, and then points you to `carousel-start` without running any stage itself. Unlike the stages, an agent may start it unasked. The prose, byte budget and skill upload checks cover it, and the installer never copies it into a project.
- **A release zip.** `node scripts/make-release-zip.js` builds `dist/carousel-os-<version>.zip`, holding exactly what `init` installs into an empty project, manifest included, so a later `update` works on the unzipped folder. A test unzips it and runs the process checks, the process tests, `generate-skills.js --confirm` and `doctor` on the result.
- The README's Install section lists the four ways to install: the one skill, npm, the release zip and a clone. A new section, Where you're needed, names the three points where the process waits on you.
- The reviewer agents are described as they are: read and search tools plus Bash for running checks, told to change nothing. The stage index names both reviewers.
- **House style stays in its lane.** In an installed project the prose check reads only `plans/`, `memory/` and the files the package installed (the manifest says which; without one, the list of what ships). A file of your own, such as `src/CHANGELOG.md`, is never prose-checked, so it can no longer stop `carousel-start`. The repository itself still checks all its prose.
- Text inside straight or curly double quotation marks, and the value of a Brief's `Literal ask:` line, is exempt from the banned-word and spelling checks, so a verbatim quote can keep its words. A word outside the quote on the same line is still checked.
- `init` and `update` print the line to add when a `CLAUDE.md` or `AGENTS.md` of yours was kept and does not mention `RULES.md`, and `doctor` and `check-process.js` fail until it does.
- The installed `.gitattributes` names only Carousel OS paths, so the rest of your repository keeps its own line endings.
- `carousel-start` names `npx carousel-os init .` when a folder is not set up.
- The README, the package description and the docs describe Carousel OS as a system for building presentations with an AI agent, with the number ledger as one part of it, and say what the number check really compares: each slide's printed numbers against that slide's ledger entry, both ways, without checking where on the slide a number sits.

## 1.0.0

The first public release. It ships the process, the checks that hold an agent to it, and a blueprint for building your own engine. It ships no engine.

- **Nine stages.** `carousel-start` through `carousel-handoff`, with `carousel-critique` running the critique rounds between storyboard and build. Each stage is a skill in `.agents/skills/<name>/SKILL.md` with a fixed report line, guards keyed on the previous stage's line, and a Real-change check. Every stage is manual-only: the front matter sets `disable-model-invocation: true` and each stage's `.agents/skills/<name>/agents/openai.yaml` sets `allow_implicit_invocation: false`, so no tool starts a stage unasked.
- **Three tools.** `.agents/skills/` is the source, used as-is by Codex and Cursor. `scripts/generate-skills.js` mirrors it into `.claude/skills/` for Claude Code. `AGENTS.md` and `CLAUDE.md` point every tool to `RULES.md`.
- **Two reviewer agents.** `agents/carousel-reviewer.md` tries to disprove the deck against the bar. `agents/carousel-fidelity.md` recomputes every number on the slides from the ledger's sources. Both start with fresh context, get read and search tools plus Bash for running checks, are told to change nothing, and return PASS, REJECT or UNVERIFIABLE with pasted evidence. Claude Code finds them in `.claude/agents/`, and any other tool can take the body as instructions.
- **A claim ledger.** One entry per slide, each number with its source and window, `checked` only after a recorded recomputation. `node scripts/check-process.js --plan` reads the slide text and native chart values out of the .pptx and compares them with the ledger.
- **A plan state machine.** `node scripts/check-process.js` checks report lines, stage order, hashes from Build to Check to Review, the REJECT cap, the prose and spelling rules, and the byte budgets for `RULES.md` and each stage file.
- **A lessons loop.** `node scripts/lessons.js` logs corrections, and only a human promotes one to a rule.
- **An installer.** `node scripts/install.js init`, `update` and `doctor`, with a manifest that never replaces a file you edited or a file of yours with the same name, and refuses any write whose real path leaves the project. Your own skills in `.agents/skills/` sit beside the stages untouched. `--no-agents` skips the `.claude/` copies. `scripts/stages.json` is the one list of the stages and agents the package ships, so a folder of yours or a stage an older version shipped is never counted as a stage. `update` removes a file only when its path is on that file's `retiredFiles` list and it is still exactly what an earlier version wrote; any other file the manifest names stays yours. When `update` keeps a stage you edited, its `.claude/` copy follows your source, a `.claude/` copy you edited yourself is never rewritten, and an unedited handoff from an older version moves to the new layout. `doctor` runs the same checks as `check-process.js` and names a kept stage that still calls a retired one. No tool in the package destroys bytes you may have written without first saving a `.carousel-backup` copy beside the file (then `.carousel-backup2`, and so on, never over an earlier backup), and each one says so on a `backup` line. A manifest from an older installer carries no format field, so every overwrite or removal against it saves a backup first; `--overwrite` always does. Its hashes are never carried into a new manifest as proof, even by a run that fails partway, and when `.claude/` copies from an earlier version remain, `update` and `doctor` name `generate-skills.js` as the fix. A plan written under an earlier layout gets one migration hint from `check-process.js` and `doctor`, and is never edited for you.
- **Line endings and safe advice.** The process hashes text (the ledger, the Build section, the config) with LF line endings, so a project checked out with `core.autocrlf=true` passes its own checks; the deck is hashed as its bytes. The installer compares text files with CRLF read as LF, so a checkout that differs only in line endings counts as unedited and gets no backup; the deck is compared as its bytes. `init` writes a `.gitattributes` (`* text=auto eol=lf`, deck binary) into a project that has none. When a project's `scripts/generate-skills.js` is not this version's, `update`, `doctor` and `check-process.js` give the same advice: it was left alone, so run the generator from your clone or the package, or update with `--overwrite`, which backs up. Printed commands name scripts by absolute path and quote paths with spaces or shell characters, so they run from any folder. A backup never writes through a symlink at its name. `generate-skills.js` refuses, and writes nothing, when a path it would write resolves outside the project. `doctor` names each engine command in `carousel.config.json` and whether its script exists (quoted paths read whole, a `-m` module or inline code reported as not checkable), and the sample config runs the example engine. Installed from a git clone, only the files git tracks ship.
- **A worked example.** A deck about an invented gym chain that was rejected once and then passed, with its plan, ledger and handoff.
- **Build your engine.** A blueprint for a scanner, renderer and drawing kit, with a small reference scanner in `docs/build-your-engine/example`.
- **A small package.** The npm package carries no images. The hero image and the gallery stay on GitHub, the README loads its image from there, and the installer leaves `docs/gallery/` out of your project.
